# Технические заметки

> **Статус:** согласовано (D-139) — требования дизайна к технике плюс выбранный стек

Этот документ не проектирует систему. Он фиксирует, **что дизайн требует от техники**, чтобы при выборе стека не выяснилось, что ключевая механика невозможна.

## Требования, вытекающие из дизайна

| Требование | Откуда | Последствие |
|---|---|---|
| Мир живёт без игроков | Асинхронность, [20-systems/01](../20-systems/01-time-model.md) | Нужен серверный тик и планировщик отложенных событий, а не только обработка запросов |
| Полное событийное логирование | Суд, метрики, расследования | Event log как первичное хранилище; состояние — производное |
| Транзакционность экономики | Деньги и предметы | Строгая согласованность на сделках. Никаких «примерно» |
| Книга заявок | [30-economy/02](../30-economy/02-markets.md) | Матчинг-движок, пусть простой |
| Права доступа на всё | Контракты, доли, должности | Гибкая модель прав, а не хардкод ролей |
| Изменяемые правила городов | [40-society/02](../40-society/02-law-engine.md) | Код-законы как данные, интерпретируемые движком, а не как ветвления в коде |
| Реальное время в чате и сценах | Живое общение, забой, торги | WebSocket / SSE |
| **Интерактивный клиент** | D-042: клики вместо команд | Полноценное SPA. **Игровой графики нет** (D-109): сцены — это панели, числа и кнопки. Отдельно стоит карта: граф-схема на SVG |
| **Масштабируемая карта-граф** | D-045 | Рендер графа с зумом и слоями; путь строится на сервере, рисуется на клиенте |
| **Хранение изображений локаций** | D-046, D-073 | Объектное хранилище, CDN, два размерных класса (баннер и фон). Загрузок в игре нет вовсе: приём и курирование живут на отдельном сайте, игра только читает готовый набор |
| **Группы внутри локации с утечками** | D-043 | Маршрутизация сообщений с вероятностью доставки в соседнюю группу |
| **Удалённое управление ордерами** | D-047 | Ордер живёт на сервере независимо от местонахождения игрока |
| Пуш-уведомления | [50-interface/04](../50-interface/04-notifications.md) | PWA или мобильное приложение |
| Античит-телеметрия | [60-meta/01](../60-meta/01-anti-cheat.md) | Хранение поведенческих метрик с первого дня |
| **Вычислительная плата за сессию** | D-110, D-112, D-113 | **Argon2id** в отдельном потоке WASM, одна оценка на сессию: `pow.memory_per_session` памяти, `pow.argon_iterations` проходов. Сервер проверяет той же оценкой — при высокой частоте стартов это нагрузка, поэтому старты сессий ограничиваются по частоте на аккаунт. Сложность **не** подстраивается под слабое устройство: иначе ферма объявит себя слабой |
| Read-only API, никакого API действий | Античит | Все действия — только через сессию клиента |
| **Балансные константы в рантайме** | D-065 | Ни одна цифра не зашита в код: конфиг с горячей перезагрузкой, админ-панель, **лог всех изменений** |
| **Процедурная генерация рецептов** | D-061, Аврора | Генератор, масштабирующий сложность по глубине комплекса |
| **Проверка различия сортов** | D-067 | Сравнение нового сорта с существующими по совокупности признаков при попытке прорастания |

**Самый нетривиальный пункт — код-законы как данные.** Если законы городов реализовать ветвлениями в коде, каждый новый тип закона потребует релиза, и вся идея «игроки пишут правила» умрёт. Нужен небольшой декларативный слой: закон = запись с типом, параметрами и областью действия, а движок при каждом действии проверяет применимые записи.

## Масштаб

Даже с интерактивным интерфейсом (D-042) серверная нагрузка остаётся скромной: нет физики, нет непрерывных позиций, нет синхронизации движения. Вся графика живёт на клиенте, сервер оперирует состояниями и транзакциями. Основная нагрузка — **транзакции, чат и рассылка событий**.

Ориентир: несколько тысяч одновременных игроков — задача, решаемая одним сервером с нормальной БД. Это принципиально проще, чем графическая MMO, и позволяет сосредоточиться на дизайне.

Узкие места, когда они появятся:
- Матчинг заявок на популярных рынках
- Рассылка сообщений в каналы
- Тик мира при большом числе длительных действий

## Выбранный стек (D-139)

### Ядро — то, без чего не начать

| Слой | Выбор | Почему именно это |
|---|---|---|
| **Язык сервера** | Python 3.12+ | Нагрузка — транзакции, чат и рассылка событий; физики и синхронизации движения нет вовсе, язык здесь не узкое место. Сборка вольта и симуляция экономики уже на Python |
| **Веб-каркас** | FastAPI + Uvicorn | Асинхронный, WebSocket из коробки, схемы запросов и ответов те же Pydantic-модели |
| **Хранилище** | PostgreSQL 16 | Транзакции без «примерно», `JSONB` под параметры законов, `LISTEN/NOTIFY` для событий, партиционирование под журнал |
| **Доступ к БД** | SQLAlchemy 2 (async) + asyncpg + Alembic | Миграции обязательны с первого дня: мир вечный, вайпов нет (D-007) |
| **Схемы и конфиг** | Pydantic v2 | `build/*.json` разбирается в типизированные модели — константа, которой нет, падает при старте, а не в бою |
| **Клиент** | React + TypeScript + Vite | Игровой графики нет (D-109): это плотное веб-приложение с реальным временем |
| **Очередь и шина** | Redis + ARQ | Четыре роли сразу: отложенные задания, тик мира, рассылка событий между процессами, ограничение частоты |

### Клиентская часть подробнее

| Задача | Чем | Почему не иначе |
|---|---|---|
| Кэш серверных данных | TanStack Query | Стаканы, цены, дела — всё это серверное состояние, а не локальное. Своё хранилище тут лишнее |
| Плотные таблицы | TanStack Table | Стакан заявок, сводка хозяйства, торговая сводка, реестр договоров — половина интерфейса это таблицы |
| Карта-граф | SVG, раскладка считается на сервере | Граф фиксирован, зум и слои — задача рендера, а не физики. Библиотека раскладки на клиенте не нужна |
| Графики цен | uPlot или visx | Лёгкие и без темы «дашборда»; тяжёлые чарт-библиотеки тянут стиль, который придётся переламывать |
| Реальное время | Нативный WebSocket | Один канал на сессию: чат локации, сцена добычи, изменения стакана |
| Уведомления | PWA + Web Push | Асинхронная игра живёт в телефоне ([04-notifications](../50-interface/04-notifications.md)) |
| Плата устройства | `argon2-browser` (WASM) в Web Worker | Одна оценка на сессию, не блокируя интерфейс (D-110, D-112) |

**Почему React, а не Svelte и не серверный рендеринг.** Svelte быстрее и меньше, но здесь выигрывает не размер бандла, а готовые решения для таблиц, доступности и клавиатурной навигации — а её требуют прямо (D-077). Серверный рендеринг отпадает по D-042: интерфейс интерактивный, со сценой добычи и картой, и постоянные полные перерисовки ему противопоказаны.

### Что добавляется позже, и по какому признаку

| Технология | Когда понадобится | Признак, что пора |
|---|---|---|
| S3-совместимое хранилище + CDN | Э2–Э3, вместе с библиотекой изображений локаций (D-046, D-073) | Появились баннеры и фоны |
| Telegram-бот | Э3 | Пуш через PWA не покрывает часть аудитории ([04-notifications](../50-interface/04-notifications.md)) |
| ClickHouse | Не раньше открытого запуска | Журнал действий перестал влезать в аналитические запросы к Postgres |

### Наблюдаемость: две разные задачи, и их путают

**Экономические метрики телеметрией не являются** и считаются **бэкендом**, а не дашбордом. Приток и отток по ресурсам, медианная цена корзины, доход в час по профессиям, инварианты И1–И13 ([04-metrics](../60-meta/04-metrics.md)) — это агрегаты игрового состояния, и они складываются в таблицы плановой задачей. Grafana их **читает, а не пересчитывает**. Ни система метрик, ни коллектор для них не нужны.

Причина не в удобстве: **торговая сводка города (D-124) — это игровой экран с той же самой агрегацией.** Ввоз, вывоз, произведено внутри, баланс товара. Агрегатор в бэкенде обязателен по игровым причинам, и вторая копия тех же формул в SQL-панелях разойдётся с первой.

**Технические метрики** — задержки, ошибки, глубина очереди, отставание тика — вторая, гораздо более скромная задача: один сервер, несколько тысяч онлайна, ни физики, ни синхронизации движения.

| Слой | Выбор | Примечание |
|---|---|---|
| **Инструментирование** | OpenTelemetry SDK, **с первого дня** | Это выбор API, а не инфраструктуры: экспорт меняется без правки кода. Автоинструментирование FastAPI, SQLAlchemy, asyncpg и Redis зрелое |
| **Хранилище метрик** | Prometheus при self-hosted, Grafana Cloud при желании не админить | Полный LGTM — пять сервисов со своими ретеншенами; для одной машины до альфы это несоразмерно |
| **Дашборд и алерты** | Grafana | **До первого плейтеста.** Без него провал экономики виден задним числом |
| **Ошибки** | Sentry либо Faro + Loki | Не метрики, а «у игрока упало, вот стек и что он делал до этого». Если уже в Grafana-стеке — Faro; если нет — SaaS Sentry дешевле возни |

**Чего не надо брать заранее:** Kubernetes, микросервисы, GraphQL, брокер сообщений тяжелее Redis, игровой движок в любом виде. Ориентир по нагрузке — несколько тысяч одновременных игроков на одном сервере с нормальной БД, и он не меняется.

## Паттерны, которые дизайн навязывает движку

Шесть мест, где реализация обязана быть устроена определённым образом. Ошибка в любом из них не ловится тестами, но ломает игру.

### 1. Тик мира обязан быть идемпотентным

Мир живёт без игроков: партии, караваны, рост урожая, суточное содержание, счётчики энергии, порча, торговая сводка. Всё это — отложенные события, и они обязаны **выполняться ровно один раз**, даже если процесс перезапустили посреди тика.

Практически: таблица заданий с состоянием и временем срабатывания, выборка через `SELECT ... FOR UPDATE SKIP LOCKED`, каждое задание завершается в одной транзакции вместе со своими эффектами. Не «крон дёргает функцию», а журнал заданий с гарантией.

### 2. Деньги — двойная запись, а не поле «баланс»

Инвариант D-127 гласит: продавец получает ровно то, что заплатил покупатель, минус налог. Проверить это на поле `balance` невозможно — расхождение обнаружится через месяц и не будет объяснимо.

Практически: неизменяемый журнал проводок, баланс — производная. Каждая сделка, налог, пошлина, жалованье и счёт за энергию — проводка со ссылкой на основание. Это же даёт готовую доказательную базу суду и метрикам.

### 3. Код-законы — интерпретируемые данные

Если законы городов сделать ветвлениями в коде, каждый новый тип закона потребует релиза, и вся идея «игроки пишут правила» умрёт.

Практически: закон — строка со ссылкой на город, типом, значением в `JSONB` и областью действия. Перед каждым действием движок собирает применимые законы и проверяет их одним проходом. Значения по умолчанию берутся из `build/laws.json` при основании города (D-130).

### 4. Константы живут в памяти, но не в коде

D-065 требует: ни одно число не зашито, изменение применяется без выката версии.

Практически: `build/constants.json` разбирается в типизированный объект при старте, поверх ложатся правки из админ-панели, каждая правка пишется в журнал изменений. Инвалидация кэша между процессами — через ту же шину, что и события. Отдельный тест обязан ловить магические числа в коде.

### 5. Агрегаты считает движок, а не дашборд

Одна формула обязана обслуживать трёх потребителей: **игровую торговую сводку** (D-124), **дашборд** и **проверку инвариантов**. Плюс четвёртого — симуляцию `tools/simulate.py`, с которой живой мир надо будет сравнивать.

Практически: плановая задача считает суточные агрегаты и пишет их в таблицы; всё остальное читает готовое. Проверка инвариантов живёт там же, потому что требует памяти между прогонами — «запас растёт две недели подряд» в панели дашборда не выражается.

За Grafana остаётся отображение, алерты поверх посчитанного и разведочные запросы руками, когда экономика повела себя странно.

### 6. Присутственное действие нельзя выставить в API

Античит держится не на защите клиента, а на том, что **API действий не существует** ([01-anti-cheat](../60-meta/01-anti-cheat.md)): всё идёт через сессию клиента с платой устройства. Публичным может быть только чтение — цены, статистика, кодекс.

Это ограничение архитектуры, а не настройка: стоит появиться удобному REST для «сделать удар», и добыча превращается в скрипт.

## Симуляция экономики

Отдельный инструмент, не часть игры: агентная модель, прогоняющая 30 игровых дней с популяцией ботов-агентов, чтобы ловить экономические катастрофы до плейтеста ([30-economy/05](../30-economy/05-balance-model.md)).

Это стоит написать **до** основного кода. Дёшево и спасает месяцы.

## Данные, которые надо хранить с первого дня

Даже если пока не используются:
- Все транзакции
- Все действия игроков с временными метками
- История цен и сделок
- История законов, приговоров, голосований

Потом восстановить это невозможно, а понадобится всё.

## Открытые вопросы

- Закрыто (D-139): стек выбран — Python, PostgreSQL, React
- Хостинг и стоимость (влияет на монетизацию)
- **Резервное копирование и откаты: как откатывать экономику после эксплойта, не разрушая доверие.** Двойная запись по деньгам делает точечный откат возможным технически, но политика отката — вопрос доверия, а не техники
