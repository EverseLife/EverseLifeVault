# Протокол сессии: двусторонний сокет

> **Статус:** принято (D-226) · **Для кого:** тот, кто делает любую функцию, которую видит клиент
>
> Сокет сессии — не «REST поверх WebSocket». Сервер говорит сам, клиент слушает. Здесь — форма сообщений, правило для новых функций и план перестройки того, что уже написано под опрос.

---

## Зачем

Сокет выбирался под живое время ([01-tech-notes](01-tech-notes.md): «один канал на сессию: чат локации, сцена добычи, изменения стакана»), но первые два года сервер только отвечал. Клиент опрашивал `look` каждые 2–5 секунд и получал целиком всё — от профиля до полки библиотеки — потому что не знал, что изменилось. Платили за это трижды: десятки запросов в базу на каждый опрос, тысячи ответов в час на игрока, и агент (D-224), которому тот же `look` шёл текстом в каждом ходу.

Ключевой факт, на котором стоит перестройка: **журнал событий уже есть** (`event`, [05-domain-model](05-domain-model.md)). Каждое изменение мира сначала становится событием, в той же транзакции, из API и из воркера. Доставить игроку — значит доставить строку этого журнала. Ничего второго изобретать не нужно.

---

## Форма сообщений

### Команда и ответ

Клиент нумерует команды; сервер возвращает номер в ответе.

```json
→ {"id": 17, "cmd": "look"}
← {"id": 17, "look": {...}}
← {"id": 18, "refused": "сначала hello"}
```

`id` — целое, уникальное в пределах соединения, выбирает клиент. Без `id` ответ тоже без `id` — старый клиент, сопоставляющий по порядку, работает; но это переходный режим, новый код так не пишет.

### Событие

Сервер шлёт сам, в любой момент после `hello`. Отличие от ответа — ключ `event`, а не `id`.

```json
← {"event": "knowledge.learned", "seq": 184213, "at": "2026-08-23T10:15:02Z",
   "touches": ["knowledge"], "recipe": "Кирка"}
```

- `event` — вид из `EventKind`, тот же, что в журнале.
- `seq` — номер строки журнала. Монотонный; по нему клиент догоняет пропущенное.
- `at` — когда случилось.
- `touches` — какие части состояния игрока это меняет (`knowledge`, `body`, `inventory`, `node`, `money`, `orders`, `chat`, …). Клиент по ним понимает, что перезапросить, **не зная самого события**. Это гарантия для нового кода: событие без рассказчика всё равно полезно.
- остальное — рассказ о событии для этого получателя; у каждого вида свой, у многих — никакого.

### Кто что получает

Событие уходит тем, кому оно **видно**, а не всем, кто подключён:

| Событие | Кому |
|---|---|
| личное (`actor` — ты, или ты назван в payload ключом `*_identity_id`: назначенный, осуждённый, продавец, принятый гражданин) | тебе, с `touches` вида |
| города (`city.*`, `justice.*`, `bank.rate_decided` с `city_id`) | каждому гражданину, где бы он ни стоял, с `touches` вида |
| узла (`node_id` задан: чат, кто вошёл и вышел, станок поставлен, участок продан) | всем, чьё тело сейчас в узле, с `touches: [node]` (рынок — `[market]`) |
| мира (`tick.ran`, `constants.changed`) | никому напрямую; клиент узнаёт через `touches` на личных |

Стороны события журнал называет **идентификаторами** (`whom_identity_id`, `defendant_identity_id`), а не именами: имя — дело рассказчика. `who` свидетелям добавляется только там, где дело на виду (пришёл, умер, уронил, назначен); торг, налог, топливо и посев для комнаты безымянны (D-047).

Подписки клиент не оформляет: личное — по личности из `hello`, узловое — по текущему узлу тела, который сервер и так знает. Переезд тела переключает узел сам.

**Рассказчик (teller)** — функция на стороне сервера: событие журнала + получатель → сообщение клиенту или ничего. Он же решает видимость сверх грубого правила выше (закрытая дверь, чужая группа D-043). Журнал хранит внутренности — id, суммы до копейки; клиенту уходит то, что он и так мог бы увидеть, спросив.

### Обрыв и догон

`hello` принимает `since` — последний полученный `seq`. Сервер досылает пропущенное из журнала через рассказчиков, затем живой поток. Предел догона — сутки (как у `happened`): дольше — клиент полностью перечитывает состояние.

Без `since` (первый вход, сброшенный кеш) — клиент сам запрашивает всё, что ему нужно, по частям.

### Части состояния вместо одного `look`

`look` остаётся — как **живая** часть: тело, путь, дела, карман, деньги, узел. Медленное уходит в свои команды и живёт в кеше клиента до события с нужным `touches`:

| Часть | Команда | `touches` | Что меняет |
|---|---|---|---|
| знания, открытия, агротех | `knowledge` | `knowledge` | `knowledge.learned`, `craft.invented` |
| профиль | `account.profile` | `profile` | `account.updated` (announce, журнала нет) |
| заказы, брони, партии | `orders` | `orders` | `market.*`, `craft.*` |
| документы на землю | `deeds` | `deeds` | `deed.*`, `land.*` |
| полка библиотеки здесь | `shelf` | `shelf` | `library.*`; и смена узла тела |

Счётчик непрочитанного в Сети остаётся в `look`: он дёшев и меняется от чужих действий.

Версии не нужны: их роль играет `seq`. Опрос `look` остаётся **только резервным** — раз в полминуты, на случай потери соединения без `onclose`. Клиент при входе читает всё разом (`look` и все части), дальше — часть за частью по `touches`; панели видят прежний `Look`, собранный из живой части и кеша (`compose()`).

## Правило для нового кода (D-226)

1. **Функция делается в расчёте на то, что сервер скажет о ней сам.** Если у действия есть последствие, которое игрок должен увидеть без своего запроса — оно событие журнала с `touches`, а при нужде с рассказчиком. Таймер на клиенте, проверяющий «не случилось ли» — не решение.
2. **Ответ на команду — подтверждение, не состояние.** Команда возвращает то, что нужно, чтобы продолжить (id, отказ, число); новое состояние приходит событием и перечитывается по `touches`. Возвращать весь `look` из команды — нет.
3. **Событие — факт журнала, не сообщение интерфейса.** Нет событий «обнови панель»; есть «кирка изготовлена», и рассказчик переводит это для клиента. Журнал — суд и метрики, он не служит транспорту.
4. **Видимость решает рассказчик.** Новый вид события, который видят не только актор и его узел, заводится вместе с правилом, кому он уходит.
5. **Агент и клиент слушают одно и то же.** Никаких событий «только для людей» или «только для агентов».

## План перестройки

Порядок — от фундамента к функциям; каждый шаг работает сам по себе и не ломает предыдущий клиент.

### Шаг 1 · Фундамент (сделан 2026-08-23)

- сервер: `id` в ответах; триггер `NOTIFY` на `event`; слушатель в процессе API; реестр сокетов по личности и узлу; рассказчики с умолчанием `touches`; `since` в `hello` с догоном
- клиент: `Session` сопоставляет по `id`, `on(event)` / `off`, догон при переподключении
- агент: разбор по `id`, буфер событий в наблюдение «что изменилось» — вместо сравнения `look`
- первые рассказчики: `chat.said`, `knowledge.learned`, `travel.arrived`, `body.*`

### Шаг 2 · Разделение `look` (сделан 2026-08-23)

- `knowledge`, `account.profile`, `orders`, `deeds`, `shelf` — свои команды; `look` — живая часть
- клиент: кеш частей, перечитывание по `touches`; опрос — резервный, 30 с
- агент: счётчики рецептов и заказов ушли из сводки; `knowledge` и `orders` модель зовёт сама

### Шаг 3 · Живые сцены (сделан 2026-08-23)

- чат локации: `chat.said` несёт саму реплику (`line`: id, who, kind, quiet, text, at; у кружка — `source`, у утечки — `overheard`); клиент добавляет строку и дедуплицирует по `id`, `chat.hear` — только при входе и после обрыва; `chat.circled` — кружки; «кто здесь» — по `travel.*`/`body.*` узла
- забой: рассказчики `mining.swing` (добыто, качество) и `mining.collapsed` (потери — только шахтёру; соседям — факт)
- стакан: `market.trade` и `market.order_placed` узлу — товар, разряд, цена, количество, **без имён**; продавец в `market.trade` — адресат
- Сеть: письмо объявляется получателю **в момент прибытия** заданием воркера `net.deliver` (сразу, если дороги нет); пост — каждому читателю по его дороге от места, где он стоит сейчас. Журнал писем не хранит (D-222) — это `announce`, не событие

### Шаг 4 · Снятие опроса (сделан 2026-08-23)

- в клиенте остался один таймер — резервный `look` раз в 30 с; сводка `world.summary`, чат, кружки, Сеть, рынок — только по событиям
- `world.summary`, `chat.hear`, `net.read` — остаются командами для чтения по событию и для догона без `since`
- метрика в `/health` → `session`: соединения, слушающие, отправленные события, ответы по командам и `look_per_connection_hour`. До перестройки — 720–1800 в час на соединение; после — резерв даёт 120 в час в простое, остальное — по делу

### Что не делается

- **Redis как шина** — не нужен: `NOTIFY` из той же транзакции, что и событие, и уже есть. Появится, если процессов API станет много и `LISTEN` на каждом окажется дорог.
- **Подписки по выбору клиента** — не нужны: видимость — свойство события, а не желание клиента.
- **Бинарная кодировка** — не даёт того, что даёт отказ от опроса (см. обсуждение 2026-08-23).
