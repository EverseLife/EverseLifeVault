# Как работать с этим репозиторием

Это **вольт гейм-дизайна Everse.Life** — внешняя память проекта. Кода игры здесь нет: он живёт в отдельном репозитории и читает отсюда `build/`.

Правила ниже существуют ради одной цели: **чтобы правка механики не превращалась в три синхронизации** — в документе, в бэкенде и во фронтенде.

---

## Два слоя, и они живут по-разному

| | **Замысел** | **Спецификация и содержание** |
|---|---|---|
| Что это | Зачем игра такая, чем платим за решение, что нельзя | Как именно считается, какие числа, какие рецепты |
| Где живёт | Markdown в этом вольте | `data/*.yaml` → `build/*.json` → движок |
| Кто источник истины | Документ, всегда | Данные и код, всегда |
| Как часто меняется | Редко, и это событие | Постоянно, и это норма |
| Из кода восстановимо | **Нет, никогда** | Да, тривиально |

Из кода никогда не вытащить, почему печать тела стоит именно 1000 энергии и что сломается при 500. Ради этого вольт и существует. Всё остальное — дублирование, и оно вычищается.

---

## Куда идёт правка

Определяется типом изменения, а не привычкой.

| Что изменилось | Что правишь | Что дальше |
|---|---|---|
| Число, коэффициент, баланс | `data/constants.yaml` | `python tools/build.py` — документ и JSON пересоберутся сами |
| Рецепт, состав, рабочая станция, тип предмета | `data/recipes.yaml` | то же |
| Закон устава, код-закон, санкция | `data/laws.yaml` | то же |
| Культура: требования, характер, цикл | `data/plants.yaml` | то же. Урожайность не задаётся — она выводится (D-136) |
| Формула, порядок шагов, вёрстка, любая реализация | только код в репозитории игры | ничего. Документ не трогаем |
| **Замысел**: механика делает не то, ради чего задумана | **сначала** запись `D-XXX` в [журнал решений](90-production/02-decision-log.md), 3–5 строк | потом один промпт агенту со ссылкой на `D-XXX` |
| Отмена принятого решения | `D-XXX` помечается отменённым, как D-022 и D-059 | промпт на снос |
| Найден дефект содержания | `OQ-XXX` в [реестр вопросов](00-core/02-open-questions.md) + `known_issues` в данных | закрывается отдельной сессией |

**Журнал решений и есть протокол синхронизации.** Он дешёвый, он объясняет агенту *почему*, и он единственное, что пишется руками при смене замысла.

## Статус документа — это контракт, а не украшение

Шапка каждого документа начинается со строки `> **Статус:** …`. Значений ровно шесть:

| Статус | Что обещает |
|---|---|
| `идея` | **Ни к чему не обязывает.** Свободное пространство, за расхождение с кодом никто не отвечает |
| `согласовано` | Решение принято и записано в журнал, кода ещё нет |
| `в реализации` | **Обязан совпадать с кодом.** Ставится, когда задача взята в работу |
| `реализовано` | **Обязан совпадать с кодом** |
| `живой` | Реестр или журнал: актуален по построению |
| `генерируется` | Собирается из `data/`. **Руками не править** |

Живой индекс всех статусов: [90-production/03-status.md](90-production/03-status.md), пересобирается вместе со всем остальным.

**Из этого следует главное правило экономии сил:** сверять с кодом нужно только `в реализации` и `реализовано`. Сегодня таких документов нет ни одного, и это честно — кода игры ещё нет.

**И второе:** документ, доезжающий до `в реализации`, обязан похудеть. Не «как считается», а «что должно быть верно и почему». Тогда после плейтеста ты крутишь коэффициент, а документ не трогаешь вообще — потому что замысел не изменился.

---

## Документ на механику пишется после плейтеста, а не до

До того как механика проверена людьми, в вольте живёт только **гипотеза и критерий провала** — так, как это сделано в [дорожной карте](90-production/00-roadmap.md). Пошагового алгоритма нет нигде, кроме кода прототипа.

Как только механика выжила — пишется короткий документ: замысел, инварианты, ссылка на модуль.

Это прямое следствие Э0 в дорожной карте: бумажные прототипы добычи **до** кода. Спецификация, написанная на механику, которая не пережила первый playtest, — чистый убыток, и синхронизировать её потом не с чем.

## Сборка

```bash
python tools/build.py
```

Читает `data/`, проверяет лестницу рецептов, пересобирает генерируемые документы, `build/*.json` и индекс статусов.

```bash
python tools/build.py --check
```

Ничего не пишет, код возврата 1 при новых проблемах. Это то, что вешается на pre-commit и в CI.

Проверка пытается **пройти лестницу с нуля** — от сырья, которое берётся руками, — и сообщает о недостижимом, зациклённом и ведущем в никуда. Уже известные расхождения перечислены в `known_issues` со ссылкой на `OQ`, и на них проверка не ругается.

Единственная зависимость: `python -m pip install pyyaml`.

## Что читает репозиторий игры

Только `build/`:

| Файл | Что внутри |
|---|---|
| `build/constants.json` | Плоская карта `ключ → значение`. Значением бывает число, строка, `{min, max}`, карта модификаторов или `{formula}`. Ни одно из этих чисел не должно быть зашито в код (D-065) |
| `build/recipes.json` | Рецепты, операции и сырьё. Поля рецепта — ниже |
| `build/laws.json` | `charter` — вопросы устава с вариантами, зависимостями и `default`; `code_laws` — параметрические законы с `default`; `sanctions` — примитивы |
| `build/plants.json` | Восемь культур: требования, характер, **выведенная** урожайность, длина цикла, щедрость и её потолок |

**Поля рецепта, и три из них меняют смысл остальных:**

| Поле | Смысл |
|---|---|
| `kind` | `station` · `tool` · `gear` · `vehicle` · `material` · `consumable` · `money`. Определяет поведение предмета в движке (D-090) |
| `inputs` | Список входов. **Если `roles: true` — это роли, а не точный состав** (D-119) |
| `amounts` | Количество каждого входа. **Выведено из трудоёмкости, а не задано** (D-133) |
| `manual_amounts` | `true` — количества заданы вручную как осмысленное исключение |
| `mix` | Состав задан пропорцией: качество зависит и от точности попадания (D-092) |
| `roles` | Входы — это роли: основа, наполнитель, жир, приправа (D-119, D-128) |
| `labor_hours` | Сколько часов труда заключено в единице. Отсюда цена-ориентир |
| `station`, `key` | На чём делается; веха лестницы |

Плюс `labor_hours` отдельной картой по всем предметам и сырью — движку она нужна для стартовых цен и оценки пошлин.

Markdown репозиторий игры не читает никогда. Если движку понадобилось значение, которого нет в `build/`, — это не повод хардкодить, а повод добавить константу в `data/constants.yaml`.

## Работа агента в этом вольте

1. **Не скармливай агенту весь вольт.** На задачу — срез из 2–4 документов плюс нужные записи `D-XXX`. Шестьдесят документов в контексте не улучшают ответ, а размывают его
2. **Числа и рецепты агент правит только в `data/`**, и после правки запускает `python tools/build.py`. Правка сгенерированного markdown будет затёрта следующей сборкой
3. **Смена замысла требует записи в журнал решений до правки кода**, а не после
4. **Термины — только из [словаря](00-core/03-glossary.md).** Ввёл новый — сразу в словарь
5. **Интерфейс описывается словами** (D-051). Схематичных макетов не делаем: они устаревают быстрее текста и создают ложное впечатление, будто визуальный дизайн решён

## Сверка кода с документами

Не после каждого коммита, а **раз в цикл плейтеста**. Один проход: сравнить фактическое поведение с документами в статусе `в реализации`, выдать список расхождений, по каждому решить — лечить код или лечить документ.

Синхронизация по расписанию дешевле синхронизации по событию. Пока в вольте нет ни одного документа `в реализации`, этот проход стоит ноль.

## Лицензии: две, и это не мелочь

Код (`tools/`, `editor/`) — под AGPL-3.0-only. Содержимое (документы,
`data/*.yaml`, шаблоны) — все права защищены, см. `CONTENT-LICENSE.md`.

Каждый файл начинается с двух строк в стиле комментариев своего языка:

    SPDX-License-Identifier: AGPL-3.0-only          — для кода
    SPDX-License-Identifier: LicenseRef-EverseLife-Content   — для содержимого
    Copyright (C) 2026 Nurlan Urazkulov

В документах это HTML-комментарий: в Obsidian и на GitHub он не виден, а в
тексте стоит первым. Новый файл заводится сразу с заголовком.

Что под какой лицензией и что не помечается вовсе (`build/`, `.obsidian/`,
сгенерированные документы) — решает `tools/spdx.py`, а не догадка. Спорный файл
дописывается в его списки, а не обсуждается с проверкой. Проверка идёт в CI,
чинится одной командой из корня:

```bash
python tools/spdx.py --apply
```

Заголовок сгенерированного документа приезжает из шаблона в `templates/` —
править его в готовом документе бесполезно, затрётся сборкой.

Чужой копирайт не трогать и не переписывать: файл с чужим копирайтом скрипт
обходит стороной и говорит об этом отдельной строкой.
